# Анализ потоков данных для process_transaction

Практическое занятие №7. Ниже используется нумерация исходного фрагмента
из задания без пустых строк. Она едина для таблиц и итогового отчёта.

```text
 1  def process_transaction(user_id, amount, db_connection):
 2      log_entry = "Start processing"
 3      if amount > 0:
 4          status = "approved"
 5          balance = get_balance(user_id)
 6          new_balance = balance - amount
 7          update_balance(user_id, new_balance)
 8      log_entry = "Transaction finished with status: " + status
 9      file = open("audit_log.txt", "w")
10      file.write(log_entry)
11      return status
```

## Цепочки Def–Use

Def — точка присваивания или связывания параметра. Use — чтение значения.
Цепочка def→use существует, если между ними значение не перезаписано
и путь исполнения достижим. Левая часть обычного присваивания — def,
а чтение переменных в правой части — use.

| Переменная | Def | Use | Достижимая цепочка и замечание |
| --- | --- | --- | --- |
| user_id | 1, параметр | 5, 7 | 1→5 и 1→7 при amount > 0 |
| amount | 1, параметр | 3, 6 | 1→3 всегда; 1→6 при amount > 0 |
| db_connection | 1, параметр | Нет | Неиспользуемый параметр, не dead store log_entry |
| log_entry | 2 и 8 | 10 | 8→10; значение из 2 не читается, его убивает def в 8 |
| status | 4, только в if | 8 и 11 | 4→8 и 4→11 при успешном положительном пути; для amount <= 0 def отсутствует |
| balance | 5 | 6 | 5→6 при успешном get_balance |
| new_balance | 6 | 7 | 6→7 при положительной сумме |
| file | 9 | 10 | 9→10: используется получатель write; освобождения ресурса нет |

Имена get_balance, update_balance и open обозначают вызываемые функции,
а не локальные переменные фрагмента. Первые два помощника предполагаются
определёнными во внешнем окружении. Если проверять фрагмент изолированно,
flake8 дополнительно обнаружит F821 для этих имён; это отдельная проблема.

## Три дефекта

**Неинициализированная переменная.** При amount <= 0 путь идёт
1→2→3→8, минуя строку 4. В строке 8 чтение status приводит к
UnboundLocalError. Строка 11 тоже содержит use status, но на этом пути
не достигается: выполнение уже прервано в строке 8. Для amount > 0
и успешных внешних вызовов status определён.

**Dead Store.** Строка 2 записывает начальное сообщение, но ни один
use этого значения не достигается. При нормальном выполнении строка 8
перезаписывает log_entry; при исключении до строки 8 значение также
не читается. Следовательно, начальное присваивание не влияет на результат.

**Resource Leak.** В строке 9 открывается файловый ресурс. В строке 10
он используется, но после неё нет close() или выхода из контекстного
менеджера. Освобождение не гарантировано ни при нормальном выходе,
ни при исключении в write. Возможное закрытие при сборке мусора
не заменяет явное управление временем жизни ресурса.

## Исправления

В [`src/fixed_transaction.py`](../src/fixed_transaction.py):

1. status получает значение pending до if, а approved — после успешного
   обновления баланса. Для нулевой и отрицательной суммы БД не вызывается.
2. log_entry присваивается один раз и затем читается при записи.
3. with open(...) гарантирует выход из файлового контекста при успехе
   и исключении. Реальное закрытие файла проверено отдельным тестом.

Дополнительно db_connection используется как адаптер с методами
get_balance(user_id) и update_balance(user_id, new_balance). Это устраняет
зависимость от неопределённых глобальных помощников. Режим a сохраняет
предыдущие записи аудита; UTF-8 и новая строка заданы явно.

Первые три позиционных аргумента сохранены. Необязательный audit_path
позволяет тестам использовать временные файлы. Ошибки БД и файловой системы
не скрываются. Отдельная транзакция БД и файловая запись не являются
единым атомарным действием; промышленный аудит потребует иной интеграции.
